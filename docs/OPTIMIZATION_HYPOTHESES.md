# Capability-Preserving Optimization: Experiment Register

These are local development dispositions, not shipped savings claims. The primary
reference is equally focused direct Astra with the task's required reasoning and
tools. No extra model call is necessary to exercise the deterministic prototypes.

| Hypothesis | Current implementation and feasibility | Validation and current disposition |
| --- | --- | --- |
| Optimization pays for itself | Context-choice comparison sums preparation, execution, verification and recovery intervals. Host overhead and retries belong in these stages. | Synthetic tests reject candidates whose preparation/recovery erase an apparent benefit. Retain the proposal-only prototype; real break-even evidence remains open. |
| Continue, compact or restart by whole cost and fidelity | Compare supported options in `context_profile.py`; do not alter host settings. Require same model, effort and snapshot plus required state/evidence/capabilities. | Tests cover changed reasoning, sources, support and state. Runtime state fidelity is unverified; defer automatic compaction/restart until supported-host matched trials pass. |

## Prospective Validation Protocol

Before paid execution, freeze task/source identities, requirements, acceptance
checks, grading rubric, arm order, permitted retries and a distinct approved total
ceiling. Existing historical allowances are not implicitly reusable.

Compare a focused direct Astra reference against one preserving candidate at a
time. Use independent tasks across coding, writing/research, images and tools,
with task-appropriate reasoning. Capture actual reported model and token counters,
cost basis, cache state, wall time, missing events and all preparatory/grading calls.
Keep engineering parent-session observations separate from attributable arm receipts.

For each arm, validate the actual result/state against the same frozen criteria.
Use independent blinded reviewers where required; owner or automated judgments
remain separately labeled. Preserve failures, cancellations, missing runs and
cheaper-but-worse outcomes in the enrollment comparator. Any quality or required
capability regression prevents promotion for that task scope.

Test state-sensitive cases explicitly: changed source after planning; altered
permissions; expired evidence; a required image; unavailable tool discovery;
contradictory evidence; interrupted state transfer; optimistic cache assumptions;
and acceptance already reached. Include at least one case where optimizing is
expected to lose, so the system must retain direct Astra.

Sample size and statistical margins require a preregistered analysis plan; a count
of passing fixtures or repeated easy tasks is not evidence of general benefits.
Record ship/revise/defer per host, task family and reasoning profile, not a global
"optimal" winner. Human validation and runtime capability gates remain open until
real evidence arrives. Current deterministic results justify engineering behavior,
not lower weekly consumption or unchanged quality across all Astra use cases.
